创建任务后会返回任务 ID，任务是异步执行的，需要轮询查询接口获取最终结果。

| 状态         | 说明   |
| ------------ | ------ |
| `queued`     | 已排队 |
| `processing` | 处理中 |
| `completed`  | 已完成 |
| `failed`     | 失败   |

建议轮询间隔为 3 到 10 秒。不要高频请求查询接口。

## 状态变化

```text
queued → processing → completed
                    → failed
```

有些任务执行很快，第一次查询就已结束；排队或准备阶段也可能直接失败。`progress` 仅作为显示进度，终止条件使用 `status`；完成时进度值可能尚未更新到 100。

## 保存与查询

创建响应收到后立即将 `id`、模型、请求时间和业务单号保存到数据库。视频用 `GET /v1/videos/{id}`，图片用 `GET /v1/images/{id}`。参考素材保留上传 UUID 和 URL，业务关联可放入创建请求的 `metadata`。

查询结果只读本次状态，HTTP `200` 还需要检查 `status`。完成时读取图片的 `url` / `images` 或视频的 `video_url`；失败时保存 `error`。`usage` 可能晚于结果补齐，结果完成与最终账务核对可以分别处理。

OpenAI 图片异步批次使用 `processing/completed/failed` 和 `/v1/images/tasks/{id}`，它的结果位于 `result.data`。见[兼容图片接口](/images/openai-compatible)。Responses 则使用[自己的响应资源](/conversation/responses)。

## 轮询与超时

- 根据任务数量和每分钟请求上限调整间隔。例如 20 个任务每 3 秒查询一次就会产生约 400 次请求/分钟，需提高间隔或减少并发。
- GET 临时失败时做退避；认证、参数和资源错误应先排查原因。
- 业务超时代表你的等待结束，已接受的任务仍可能继续执行。保留任务 ID，稍后继续查询或在工作台核对。
- 创建请求超时且未拿到 ID时，先检查任务历史及业务单号。再次创建会产生新的任务。
- 当前这些直接图片/视频创建接口采用轮询方式，文档没有可配置的任务 Webhook 参数。
